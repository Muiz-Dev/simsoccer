# Virtual Football Engine

## Dynamic Simulation, Mathematical Model, Database, Team Evolution and Betting-System Architecture

**Document type:** Engineering and system-design specification
**System:** Original virtual football simulation platform
**Primary objective:** Build a persistent, mathematically coherent virtual football universe whose teams, players, matches, statistics, leagues, markets and historical state evolve over time.

---

# 1. The Core Idea

The most important architectural decision is this:

> **We are not building a betting website that happens to generate football results.**

We are building:

> **a virtual football universe that happens to expose betting markets.**

The football universe is the source of truth.

The betting system is a consumer of that universe.

This distinction determines almost every important engineering decision.

The system should maintain a persistent world containing:

* leagues
* seasons
* clubs
* squads
* players
* player attributes
* managers
* tactical systems
* injuries
* fatigue
* morale
* team form
* attacking strength
* defensive strength
* goalkeeping strength
* set-piece strength
* discipline
* possession tendency
* tempo
* pressing intensity
* defensive line
* chance creation
* finishing
* corners
* fouls
* cards
* substitutions
* home advantage
* historical performance
* team development
* player development
* fixture history
* match statistics
* league tables
* market probabilities
* market odds
* betting exposure
* and historical snapshots of the entire system.

A match should therefore be the **result of the current state of this world**, not an isolated random event.

---

# 2. What "The System Shapes Itself" Means

When we say the system should shape itself, we mean that we should avoid manually determining every future outcome.

For example, we should not write:

```text
Liverpool strength = 91
Chelsea strength = 84
Arsenal strength = 89
Manchester United strength = 82
```

and leave those numbers permanently fixed.

Instead, the system starts with an initial state.

After that, the state evolves.

For example:

```text
Initial team state
        ↓
Players + tactics + squad quality
        ↓
Match
        ↓
Goals
Corners
Shots
Fouls
Cards
Possession
xG
Substitutions
        ↓
Post-match evaluation
        ↓
Team state update
        ↓
Player state update
        ↓
Form update
        ↓
Confidence / morale update
        ↓
Injury / fatigue update
        ↓
Next match
```

Therefore:

```text
Match 1
   ↓
changes Team State
   ↓
Match 2
   ↓
changes Team State
   ↓
Match 3
   ↓
changes Team State
```

This is the foundation of the system.

---

# 3. Important Principle: Randomness Is Not the Same as Unpredictability

A sophisticated simulator should not simply use:

```typescript
Math.random()
```

everywhere.

That creates independent randomness.

Instead, randomness should be applied **inside a structured mathematical model**.

For example:

```text
Team strength
+
Player strength
+
Tactics
+
Home advantage
+
Fatigue
+
Form
+
Injuries
+
Match state
+
Random variation
=
Match behaviour
```

The random component creates uncertainty.

The mathematical state creates structure.

That is what makes the world believable.

# 4. Three Different Layers of "Strength"

A major improvement over the original design is to stop thinking of a team as having one strength number.

A team should have several interacting strengths.

## 4.1 Team latent strength

This is the underlying ability of the team.

For example:

```text
overallAbility
attackAbility
defenceAbility
goalkeepingAbility
creationAbility
setPieceAbility
discipline
pressing
possession
transition
```

These should not necessarily be directly visible to the user.

---

# 5. Team Strength Should Be Derived

Instead of storing only:

```text
strength = 86
```

we should store something closer to:

```text
attack_rating
defence_rating
creation_rating
finishing_rating
goalkeeping_rating
pressing_rating
transition_rating
set_piece_rating
discipline_rating
fitness_rating
```

Then derive overall performance from them.

For example:

```text
overall_strength =
    0.24 × attack
  + 0.20 × defence
  + 0.14 × creation
  + 0.12 × finishing
  + 0.10 × goalkeeping
  + 0.08 × transition
  + 0.05 × pressing
  + 0.04 × set_piece
  + 0.03 × discipline
```

The weights should be configuration rather than hard-coded.

This allows us to tune the engine later.

---

# 6. But Even Those Ratings Should Not Be Completely Static

The system should distinguish between:

### Permanent ability

What a player or team is fundamentally capable of.

### Current form

How well that ability is currently being expressed.

### Current availability

Whether the player is actually available.

### Match readiness

Fatigue, fitness, recovery and workload.

### Tactical suitability

Whether the player's characteristics fit the current tactical system.

### Random match variance

The uncertainty inherent in football.

Therefore:

```text
effective_player_strength
=
base_ability
× form_modifier
× fitness_modifier
× tactical_fit
× morale_modifier
× development_modifier
```

with carefully controlled bounds.

For example:

```text
Player

├── acceleration
├── stamina
├── strength
├── positioning
├── passing
├── vision
├── crossing
├── dribbling
├── finishing

├── heading

├── marking
├── composure
├── concentration
├── aggression
├── discipline
├── goalkeeper_reflexes
├── goalkeeper_positioning
└── goalkeeper_handling
```

Not every player needs every attribute to be meaningful.

# 8. Player Roles

Players should have roles.

Examples:

```text
GK

LB
RB
LWB
```

For example:

```text

```

This matters because tactical systems should not treat every player identically.

---

# 9. Player Ability Is Not the Same as Player Rating

A player could have:

```text
passing = 91
finishing = 61
pace = 78
vision = 94
```

and still have a high overall rating because they are a creative midfielder.

Another player might have:

```text
passing = 68
finishing = 94
pace = 90
```

and be an elite striker.

Therefore, player ratings should be role-dependent.

---

# 10. Player Development

Players should evolve.

A simple development model could be:

```text
new_ability =
    old_ability
    + development_rate
    × age_curve
    × training_quality
    × playing_time
    × potential_factor
    + development_noise
```

Young players can improve faster.

Prime-age players can remain relatively stable.

Older players can decline gradually.

But the system should not make development deterministic.

A young player with high potential might:

```text
+2.1
+0.8
+1.7
+0.3
```

across several periods.

Another could stagnate.

---

# 11. Potential Should Not Mean Guaranteed Growth

Do not implement:

```text
potential = 95

therefore player eventually becomes 95
```

Instead:

```text
potential = upper capability distribution
```

The player's development probability depends on:

* age
* training
* playing time
* injuries
* coaching
* tactical usage
* performance
* consistency
* development variance

This makes the player system less predictable.

---

# 12. Player Decline

Decline should also be gradual.

For example:

```text
physical decline
mental decline
recovery decline
injury susceptibility
```

can increase with age.

But again:

> Do not make age alone determine performance.

A technically gifted older player may retain excellent passing and vision while losing pace.

---

# 13. Team Strength From Players

The team's strength should be calculated partly from its squad.

For example:

```text
starting XI
    ↓
weighted player abilities
    ↓
positional aggregation
    ↓
team attacking ability
team defensive ability
team creation ability
team transition ability
team goalkeeping ability
```

A possible structure:

```text
Team Attack

ST finishing
+ winger creation
+ midfielder creation
+ fullback crossing
+ tactical modifiers
```

and:

```text
Team Defence

CB defending
+ fullback defending
+ DM protection
+ goalkeeper
+ defensive tactic
```

# 14. Squad Depth Matters

A team should not have only:

```text
starting XI
```

It should have:

```text
starting XI
bench
rotation players
academy/development players
```

This becomes important when:

* injuries occur
* suspensions occur
* fatigue increases
* congested fixtures occur
* managers rotate players

# 15. Manager and Tactical System

Eventually, each team should have a manager profile.

The manager could have:

```text
attacking_tendency
defensive_tendency
pressing_tendency
rotation_tendency
risk_tolerance
substitution_tendency
formation_preference
youth_preference
```

A manager should influence tactics, not directly determine results.

# 16. Tactical Model

Examples:

```text
4-3-3
4-2-3-1
4-4-2
3-5-2
3-4-3
5-3-2
```

Tactics should modify match parameters.

For example:

### High pressing

Potential effects:

```text
+ possession recovery
+ turnovers
+ attacking opportunities
+ fouls
+ fatigue
- late-match stamina
```

### Deep block

Potential effects:

```text
- opponent penetration
- possession
+ counterattack opportunities
- attacking volume
```

### High defensive line

Potential effects:

```text
+ territorial pressure
+ offside opportunities
+ possession
- vulnerability to pace
```

These are not fixed truths; they are model parameters that we calibrate.

# 17. The Match Should Have a Latent State

This is where the system becomes much more sophisticated.

A match should have a state such as:

```text
possession_home
possession_away

attacking_pressure_home
attacking_pressure_away

momentum_home
momentum_away

fatigue_home
fatigue_away

risk_home
risk_away

discipline_home
discipline_away

tempo
```

The values evolve during the match.

---

# 18. Momentum

Momentum should not mean:

> Team scored, therefore automatically scores again.

That would be too simplistic.

Instead, a goal can modify:

```text
risk appetite
confidence
tactical state
opponent urgency
pressing
defensive compactness
```

For example, if Home is losing 0–1 at minute 75:

```text
home_risk ↑
home_attack_intensity ↑
home_defensive_exposure ↑
away_counterattack_probability ↑
```

This produces realistic interactions.

# 20. Goal Simulation

The basic mathematical foundation can begin with a Poisson model.

For a team:

```text
P(X = k) = e^-λ × λ^k / k!
```

where:

```text
λ = expected goals
```

This is not our complete simulator.

It is the statistical foundation for goal generation.

Established football modelling has used Poisson-style models with team attack and defensive parameters, while later models introduce correlations and dynamic team strengths.

---

# 21. Expected Goals Should Be Derived

We should calculate:

```text
λ_home
λ_away
```

from multiple factors.

For example:

```text
λ_home =
    league_home_goal_rate
    × home_attack_strength
    × away_defensive_weakness
    × home_advantage
    × form_modifier
    × lineup_modifier
    × tactical_modifier
    × fatigue_modifier
```

Similarly:

```text
λ_away =
    league_away_goal_rate
    × away_attack_strength
    × home_defensive_weakness
    × form_modifier
    × lineup_modifier
    × tactical_modifier
    × fatigue_modifier
```

Then clamp extreme values.

For example:

```text
λ >= 0.15
λ <= 4.50
```

The exact boundaries should be configurable.

---

# 22. Home Advantage Should Be Dynamic

Do not simply say:

```text
home advantage = +0.30
```

forever.

Instead:

```text
home_advantage =
    league_base_home_advantage
    × team_home_effect
    × current_environment_modifier
```

A team's historical home performance can gradually influence its home effect.

---

# 23. Team Ratings Should Update After Matches

This is one of the most important systems.

After every match:

```text
predicted performance
        ↓
actual performance
        ↓
error
        ↓
rating update
```

For example:

```text
expected_home_goals = 1.8
actual_home_goals = 3

unexpectedly strong attacking result
```

This should contribute to an update.

But one match should not radically transform the team.

---

# 24. Dynamic Team Rating

A basic update can look like:

```text
new_attack =
    old_attack
    + learning_rate
      × observation_error
```

where:

```text
observation_error =
    actual_performance
    - expected_performance
```

A more sophisticated implementation should use a state-space model.

The statistical literature explicitly supports treating team ability/form as a changing latent state rather than a fixed number.

---

# 25. Use Multiple Time Scales

This is critical.

Not every factor should change at the same speed.

For example:

| Factor               | Update speed   |
| -------------------- | -------------- |
| Match momentum       | minutes        |
| Fatigue              | minutes/hours  |
| Form                 | matches        |
| Tactical familiarity | matches        |
| Team rating          | matches        |
| Player development   | weeks/months   |
| Player ageing        | months/seasons |
| Club identity        | seasons        |

This prevents the simulator from becoming unstable.

---

# 26. Exponential Form Memory

A useful approach is exponentially weighted performance.

For example:

```text
form_t =
    α × current_performance
    +
    (1 - α) × form_(t-1)
```

If:

```text
α = 0.15
```

recent matches matter, but historical performance remains relevant.

Different attributes can use different α values.

---

# 27. Bayesian / State-Space Upgrade

Eventually we can represent team ability as:

```text
θ_t = θ_(t-1) + process_noise
```

Then:

```text
observed_match_performance
=
function(θ_t)
+
observation_noise
```

This means the system understands:

> "I do not know exactly how strong this team currently is."

Instead, it maintains an estimate.

For example:

```text
Team attack:

mean = 83.7
uncertainty = 4.2
```

After more matches:

```text
mean = 84.1
uncertainty = 2.8
```

The system becomes more confident as evidence accumulates.

This is considerably more sophisticated than a simple Elo number.

---

# 28. Use a Hybrid Rating System

I recommend eventually using three layers:

```text
LONG_TERM_ABILITY
        +
CURRENT_FORM
        +
MATCH_STATE
```

For example:

```text
effective_attack =
    0.65 × long_term_attack
  + 0.25 × form_attack
  + 0.10 × tactical_match_effect
```

Then add player availability and match-specific modifiers.

---

# 29. Do Not Let Bets Determine Match Results

This needs to be explicit.

Suppose:

```text
10,000 users bet Home
```

The simulator must **not** say:

```text
too much money on Home
→ reduce Home's chance
```

That would make the football outcome dependent on customer behaviour.

Instead:

```text
Football engine
       ↓
true probability distribution
       ↓
market engine
       ↓
odds
```

And separately:

```text
Users
 ↓
bets
 ↓
exposure
 ↓
risk management
```

The betting system can react to exposure by:

* changing displayed prices
* limiting stakes
* suspending markets
* changing liquidity
* flagging unusual activity

But the match simulation remains independent.

---

# 30. Why This Separation Matters

If betting influences the match:

```text
bet
→ outcome
→ settlement
→ future statistics
```

you have created a feedback loop.

That can cause:

```text
market behaviour
→ football outcome
→ market behaviour
```

which is not desirable for a clean simulation.

Instead:

```text
WORLD
 ↓
MATCH
 ↓
RESULT
 ↓
MARKETS
 ↓
BETS
```

Bets are downstream.

---

# 31. The Market Engine

The market engine reads the probability distribution.

Suppose the score model produces:

```text
P(0-0)
P(1-0)
P(0-1)
P(1-1)
P(2-0)
...
```

From this we derive:

```text
P(Home Win)
P(Draw)
P(Away Win)
```

and:

```text
P(BTTS)
P(Over 1.5)
P(Over 2.5)
P(Over 3.5)
```

etc.

# 32. Corners Need Their Own Model

Do not generate corners as:

```text
corners = goals + random number
```

Corners are a separate event process.

We can model:

```text
corner_intensity_home
corner_intensity_away
```

using:

```text
attacking pressure
possession
crossing
wing usage
shots
blocked shots
opponent defensive pressure
game state
tempo
```

Then generate corner events.

A Negative Binomial distribution can later be considered if observed variance exceeds what a Poisson model handles well.

---

# 33. Fouls Need Their Own Model

Fouls should depend on:

```text
pressing
aggression
tackling
possession imbalance
match intensity
fatigue
scoreline
referee profile
```

For example:

```text
foul_rate =
    base_rate
    × intensity
    × pressing
    × aggression
    × fatigue
    × match_state
```

---

# 34. Yellow Cards Need to Depend on Fouls

Do not independently generate:

```text
fouls = 17
yellow_cards = 6
```

Instead:

```text
foul
 ↓
severity
 ↓
referee interpretation
 ↓
card probability
```

Therefore:

```text
yellow_cards ⊂ foul events
```

rather than two unrelated random numbers.

---

# 35. Red Cards

A red card can result from:

```text
direct_red_probability
```

or:

```text
yellow_card
+
second_yellow_probability
```

Then the red card changes the match state.

For example:

```text
player_removed
↓
team_players = 10
↓
defensive strength decreases
↓
fatigue increases
↓
opponent attacking probability changes
```

This is exactly what we want.

---

# 36. Substitutions

Substitutions should have causes.

Possible triggers:

```text
fatigue
injury
yellow card
poor performance
tactical change
scoreline
minute
manager tendency
```

Then the replacement player's attributes change the team's effective state.

---

# 37. Injuries

Injury probability should depend on:

```text
player_age
fatigue
minutes_played
injury_history
physical_attributes
match_intensity
```

Example:

```text
injury_probability =
    base_injury_rate
    × fatigue_factor
    × age_factor
    × history_factor
    × intensity_factor
```

An injury then becomes persistent state.

---

# 38. Fatigue

Fatigue should accumulate.

For example:

```text
fatigue_after_match =
    fatigue_before
    + minutes
    × intensity
    - recovery
```

Recovery occurs between matches:

```text
fatigue_after_recovery =
    fatigue × recovery_rate
```

This becomes important when fixtures are close together.

---

# 39. Fixture Congestion

If a team plays:

```text
Saturday
Tuesday
Friday
Monday
```

the squad should behave differently from a team playing once every seven days.

This creates another emergent factor.

---

# 40. Discipline as a Persistent Attribute

Teams can develop different disciplinary tendencies.

For example:

```text
team_aggression
team_discipline
manager_aggression
player_aggression
```

The observed foul/card behaviour feeds back into future estimates.

---

# 41. Referee Model

If we eventually have referees, each referee can have:

```text
foul_tolerance
yellow_rate
red_rate
penalty_rate
advantage_tendency
```

The referee does not decide outcomes directly.

The referee modifies the probability of disciplinary events.

---

# 42. Weather / Environment

This can eventually be added.

For example:

```text
rain
heat
wind
pitch_quality
```

These can influence:

```text
passing

fatigue
shots

```

For a purely virtual system, these can be simulated rather than sourced from real weather.

# 43. Match Event Correlation

This is extremely important.

The events should not be independent.

For example:

```text
high possession
→ more attacks

more attacks
→ more shots

more shots
→ more blocked shots

blocked shots
→ more corners

high pressing
→ more recoveries

high pressing
→ more fouls

more fouls
→ more cards

fatigue
→ lower pressing

lower pressing
→ more opponent possession
```

This creates a network.

That network is what makes the simulator feel alive.

# 45. Scoreline Should Influence Tactics

This is another major source of realism.

At:

```text
0-0, minute 20
```

both teams may be relatively balanced.

At:

```text
0-1, minute 78
```

the losing team should become more aggressive.

At:

```text
2-0, minute 82
```

the winning team may reduce risk.

Therefore:

```text
scoreline → tactical state → event probabilities
```

---

# 46. Do Not Overuse "Momentum"

Momentum is useful, but dangerous.

If implemented badly:

```text
team scores
→ momentum +20
→ another goal
→ momentum +20
→ another goal
```

This produces unrealistic goal cascades.

Instead, use bounded effects:

```text
momentum ∈ [-1, +1]
```

and let it decay:

```text
momentum_t =
    momentum_(t-1) × decay
    + event_shock
```

# 47. Match Simulation Architecture

The match simulator should have distinct stages.

```text
1. Load world state

2. Load teams

3. Load available players

4. Select lineups

5. Load tactics

6. Calculate pre-match state

7. Calculate probability distributions

8. Generate match random seed

9. Simulate match

10. Validate result

11. Generate event timeline

12. Persist authoritative result

13. Update player statistics

14. Update team statistics

15. Update ratings

16. Update injuries/fatigue

17. Update league table

18. Generate market settlement data
```

---

# 48. Deterministic Seeds

Every match should have a seed.

For example:

```text
seed =
SHA256(
    season_id
    + fixture_id
    + simulation_version
    + world_version
)
```

The actual implementation can use a proper seeded random generator.

Your existing package includes `seedrandom`, which is useful for this purpose.

This gives us:

```text
same world state
+
same seed
+
same simulation version
=
same result
```

That is extremely valuable for debugging.

---

# 49. Simulation Versioning

Every match should record:

```text
simulation_version
```

For example:

```text
2026.1
2026.2
2026.3
```

If we change the mathematics later, old matches should not suddenly change.

# 50. World Version


Therefore a match might contain:


# 183. The Fundamental Rule

The most important rule for the entire project should be:

> **Every major number in the system should either be an observed fact, an explicitly configured prior, or a mathematically derived state.**

We should avoid arbitrary numbers appearing throughout the code.

Bad:

```typescript
if (team === "arsenal") {
    strength += 7;
}
```

Good:

```text
team state
→ player state
→ tactical state
→ statistical model
→ probability
```

---

# 184. Second Fundamental Rule

> **Every dynamic change should have a cause.**

If a team becomes stronger:

```text
Why?
```

Possible answer:

```text
improved player performance
```

or:

```text
player development
```

or:

```text
tactical adaptation
```

or:

```text
squad improvement
```

or:

```text
statistical evidence caused rating update
```

Not:

```text
randomly increased strength by 3.
```

---

# 185. Third Fundamental Rule

> **Randomness should create uncertainty, not replace the model.**

The engine should not say:

```text
randomly decide everything.
```

It should say:

```text
given the current state,
these outcomes have these probabilities,
and randomness chooses one realization.
```

---

# 186. Fourth Fundamental Rule

> **Markets observe the football universe; they do not secretly control it.**

This gives us a clean architecture:

```text
WORLD
 ↓
MATCH
 ↓
PROBABILITIES
 ↓
ODDS
 ↓
BETS
```

rather than:

```text
BETS
 ↓
change match result
```

---

# 187. Fifth Fundamental Rule

> **Historical state must never disappear.**

Never simply overwrite:

```text
team rating
player rating
match result
odds
```

without preserving the historical transition.

The system should eventually be capable of reconstructing:

```text
"What did the world look like immediately before Match 4,218?"
```

That is what turns this from a toy random-number generator into an actual simulation platform.
