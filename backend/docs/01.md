**Project type:** Autonomous virtual football simulation platform
**Backend:** Node.js + TypeScript + Express 5
**Database:** PostgreSQL / Supabase
**ORM:** Drizzle ORM

# 1. Executive Summary

SIM SOCCER is an autonomous virtual football universe.

It is not primarily a betting application.

The correct way to think about the system is:

> **SIM SOCCER is a football simulation engine that happens to expose football markets and a betting interface.**

The football universe must exist independently of betting.

The system should therefore be capable of:

* creating leagues;
* creating seasons;
* creating teams;
* assigning team strengths;
* generating fixtures;
* simulating matches;
* generating final scores;
* generating chronological match events;
* maintaining league tables;
* maintaining team statistics;
* scheduling future matches;
* broadcasting live match events;
* calculating market probabilities;
* generating play-money odds;
* accepting simulated bets;
* settling bets;
* maintaining wallet ledgers;
* recording complete audit information;
* recovering after server crashes;
* preventing duplicate processing;
* reproducing a match from its original simulation seed;
* running continuously without human intervention.

The current project blueprint already describes this overall lifecycle: pre-generation of matches, market closure at kickoff, chronological broadcasting, settlement, and league progression.

The purpose of this document is to turn that idea into an actual engineering specification.

# 5. Most Important Architectural Principle

Do not put the football simulation inside an Express route.

Bad:

```text
POST /simulate-match
        ↓
Express
        ↓
generate score
        ↓
generate events
        ↓
save everything
```

Instead:

```text
Simulation Engine
        ↓
Simulation Result
        ↓
Persistence
        ↓
Scheduled Match
        ↓
Broadcast Worker
        ↓
WebSocket
```

The simulation engine should be usable without HTTP.

For example:

```typescript
const result = simulateMatch(context);
```

should work from:

* a test;
* a command-line script;
* a BullMQ worker;
* an admin simulation tool;
* a season generator;
* a statistical analysis script.

That separation will save you enormous problems later.

# 11. JWT Authentication

Your project already has:


and:


The important point is that we should not blindly decode JWTs.

The server must verify:

* signature;
* issuer;
* audience;
* expiration;
* subject.

Supabase provides a JWKS endpoint for asymmetric signing keys and documents local JWT verification using the public keys.

# 16. Team Strength

A simple first implementation can use:

```text

defense_strength
overall_rating
```

Example:

```text
Team A

attack = 1.18
defense = 0.91
overall = 82
```

Important:

Decide what `defense_strength` means.

There are two possible conventions.

### Convention A

Higher means stronger defense.

```text
1.20 = excellent
1.00 = average
0.80 = weak
```

### Convention B

Higher means more goals conceded.

```text
1.20 = weak
1.00 = average
0.80 = strong
```

The old blueprint uses Convention B in some sections.

I recommend Convention A because it is easier to understand:

```text
1.20 = 20% better than league average
0.80 = 20% worse than league average
```

Then the formula can explicitly invert the defensive strength.

# 24. Poisson Distribution

For goals:

$$
P(X=k)=\frac{\lambda^k e^{-\lambda}}{k!}
$$

For example, if:

```text
λ = 1.50
```

the probability of exactly two goals is:

$$
P(2)=\frac{1.5^2e^{-1.5}}{2!}
$$

The engine should calculate this programmatically.

Do not hard-code probabilities.

# 25. Score Matrix

Generate:

```text
0-0
0-1
0-2
...
6-6
```

or preferably calculate a sufficiently large range such as:

```text
0–10
```

and normalize.

The old blueprint proposes a 7×7 matrix from 0 through 6.

That is acceptable for an initial prototype, but the implementation should handle the probability tail correctly.

If you truncate the distribution at six goals, do not blindly assume the probabilities still sum to exactly 1.

Instead:

```text
sum(matrix)
```

then either:

1. include enough goal values that the omitted tail is negligible; or
2. normalize the matrix.

# 26. Exact Score Probability

If goals are treated as independent:

$$
P(Home=i,Away=j)
=
P(Home=i)\times P(Away=j)
$$

Therefore:

```text
P(2-1)
=
P(Home = 2)
×
P(Away = 1)
```

This produces the scoreline matrix.

# 29. Important Improvement: Seeded Does Not Mean "Secure"

A deterministic seed is excellent for reproducibility.

It is not automatically sufficient for a real-money gambling product.

For a personal/play-money system:

```text
seeded PRNG
```

is perfectly reasonable.

For a regulated commercial gambling product, randomness, game integrity, auditing, certification, key management, and regulatory requirements would require a substantially different security/compliance process.

Therefore the project should explicitly distinguish:

```text
DEVELOPMENT / PLAY MONEY
```

from:

```text
REGULATED REAL MONEY
```

Do not design the current prototype as though passing a seeded PRNG automatically makes it suitable for regulated gambling.

# 31. Do Not Make Events Independent of the Final Score

This is a critical rule.

If the final score is:

```text
2–1
```

the timeline must contain exactly:

```text
2 home goals
1 away goal
```

It must never generate:

```text
3 home goals
```

and then separately discover that the final result was 2–1.

The final score is authoritative.

The event timeline is a chronological representation of that result.

---

# 32. Timeline Generation Algorithm

For a 2–1 result:

### Step 1

Create three goal slots.

```text
HOME
HOME
AWAY
```

### Step 2

Generate three goal times.

### Step 3

Prevent impossible collisions.

### Step 4

Sort chronologically.

### Step 5

Assign the goal events.

Example:

```text
HOME → 17:31
AWAY → 54:09
HOME → 83:42
```

---

# 33. Goal Timing Distribution

Do not make every minute equally likely if you want a realistic-looking simulation.

However, do not hard-code the claim that "minute 90 is always more likely" as though it were a law of football.

Instead define a configurable distribution:

```text
early match
mid first half
late first half
early second half
mid second half
late second half
```

For example:

```text
0–15
15–30
30–45
45–60
60–75
75–90
```

Each period receives an intensity weight.

The exact weights should be configurable and statistically tested.

# 47. Do Not Rely Only on Redis Locks

Your original blueprint proposes Redis mutex locking for the double-tick problem.

That is useful, but it should not be the only protection.

The strongest design is:

```text
Redis lock
+
database state transition
+
unique constraints
+
idempotent operations
```

For example:

```text
UPDATE fixtures
SET status = 'FINISHED'
WHERE id = ?
AND status = 'LIVE'
```

Then check how many rows were updated.

If:

```text
1 row
```

you won.

If:

```text
0 rows
```

another process already completed it.

This is safer than trusting only a distributed lock.

# 54. Probability Engine

The probability engine should calculate:

```text
P(Home Win)
P(Draw)
P(Away Win)
```

from the score matrix.

For example:

```text
Home Win =
sum(P(homeScore > awayScore))

Draw =
sum(P(homeScore === awayScore))

Away Win =
sum(P(homeScore < awayScore))
```

---

# 55. Over/Under

For:

```text
Over 2.5
```

calculate:

```text
homeScore + awayScore >= 3
```

For:

```text
Under 2.5
```

calculate:

```text
homeScore + awayScore <= 2
```

---

# 56. BTTS

Both teams score:

```text
homeScore >= 1
AND
awayScore >= 1
```

Sum all corresponding score probabilities.

---

# 57. Correct Score

```text
P(homeScore = X, awayScore = Y)
```

```text

```

```text

```

# 58. Fair Odds

If:

```text

```

then:

```text

           = 2.00
```

The old blueprint uses this same basic approach.

# 59. Margin

For play-money simulation, you can apply a configurable margin.

For example:

```text
target margin = 0.08
```

However, do not blindly use:

```text
fair odds / 1.08
```

for every market and assume the resulting probabilities behave correctly.

Instead, build an odds-pricing module that:

1. calculates fair probabilities;
2. normalizes them;
3. applies the desired overround;
4. converts to decimal odds;
5. rounds according to configured rules;
6. verifies the resulting margin.

This gives you much more control.

# 142. Unexpected Scenarios

You specifically asked that we consider unpredictable outcomes.

This should be treated as a first-class engineering requirement.

---

## Scenario: Server crashes during a goal

The goal must not disappear permanently.

Use:

```text
persistent event record
+
sequence number
+
broadcast status
```

---

## Scenario: Goal is broadcast twice

The frontend should detect duplicate:

```text
fixtureId + sequence
```

and ignore the duplicate.

The backend should also make broadcasting idempotent.

---

## Scenario: User refreshes during a goal

The client requests current state.

It does not depend on having witnessed every WebSocket event.

---

## Scenario: Bet request arrives exactly at kickoff

The server decides based on authoritative transaction time/state.

If the fixture has already transitioned:

```text
LIVE
```

the pre-match bet is rejected.

---

## Scenario: Odds changed milliseconds before bet

The bet request contains the expected odds/version.

If it no longer matches:

```text
ODDS_CHANGED
```

and the user must confirm again.

---

## Scenario: Wallet has insufficient funds

Reject atomically.

Never:

```text
create bet
then discover insufficient balance
```

---

## Scenario: Two bets arrive simultaneously

Database transaction and wallet locking must prevent overspending.

---

## Scenario: Redis lock expires

Database state transitions and idempotency must still prevent duplicate settlement.

---

## Scenario: Worker dies during settlement

The job can be retried.

Because settlement is idempotent, retrying does not produce a second payout.

---

## Scenario: Database transaction succeeds but HTTP response is lost

The client retries.

The idempotency key allows the API to return the original result instead of creating another bet.

---

## Scenario: WebSocket server dies

Client reconnects.

The server sends current state.

---

## Scenario: Simulation code changes

Old simulations remain tagged:

```text
simulationVersion = 1.0.0
```

New matches use:

```text
1.1.0
```

---

## Scenario: Team rating is accidentally invalid

Zod/domain validation rejects:

```text
attack = -500
```

or:

```text
defense = Infinity
```

---

## Scenario: Fixture is duplicated

Database unique constraints prevent it.

---

## Scenario: Season generation runs twice

Use an idempotent season-generation operation.

---

## Scenario: Match is already finished

Settlement worker sees:

```text
settled = true
```

and exits safely.

---

## Scenario: Client manipulates odds

The server ignores client-supplied authoritative odds.

---

## Scenario: Client manipulates stake

The server validates:

```text
stake > 0
stake <= permitted maximum
```

---

## Scenario: Client sends fake match result

Ignored.

Only the simulation/fixture system can determine the result.

# 169. The Most Important Design Rules

Keep these rules visible in the repository README.

### Rule 1

**The simulation engine is independent from Express.**

### Rule 2

**PostgreSQL is the authoritative permanent state.**

### Rule 3

**Redis is an acceleration and coordination layer, not the permanent source of truth.**

### Rule 4

**The frontend never determines authoritative results.**

### Rule 5

**Every simulation is reproducible from its version and seed.**

### Rule 6

**Every important financial operation is transactional and idempotent.**

### Rule 7

**Every match has an explicit state machine.**

### Rule 8

**Every event has an ordered sequence number.**

### Rule 9

**Old simulation versions are never silently replaced.**

### Rule 10

**Build the football universe before building the betting interface.**
